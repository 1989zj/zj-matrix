## 1. 设计目标

### 1.1 问题定义

番茄 AI 文最大死因——**「打脸→震惊→消费→再打脸」无限循环**，20 万字后必腻。V2 的 anti-repetition 系统仅做逐章重复检测（得分 >0.30 则退回重写），缺乏对**累积性疲劳**的感知和主动性干预。

| 问题 | V2 anti-repetition | V3 anti-fatigue |
|------|-------------------|-----------------|
| 检测粒度 | 单章 vs 历史 50 章 | 累积周期检测 + 趋势预测 |
| 干预能力 | 仅退回重写 | 主动触发地图/副本/势力/节奏变更 |
| 与 ARC 集成 | 无 | 疲劳得分直接影响 ARC 调整决策 |
| 检测维度 | 7 维"重复"检测 | 7 维"疲劳"检测（含密度、间隔、曲线） |
| 输出用途 | 单章通过/拒绝 | 全局健康度 + 干预建议 |

### 1.2 核心理念

```
疲劳 ≠ 重复
重复是"又出现了一样的东西"
疲劳是"读者已经对这个模式感到厌倦"
→ V3 检测的是疲劳信号，而非简单的字符串/模式匹配
```

### 1.3 系统边界

- **输入**: 最近 N 章（检测周期默认 20 章）的章节记忆 + 历史检测记录
- **输出**: 疲劳评分 + 各维度明细 + 干预建议（若触发阈值）
- **不负责**: 实际执行干预（由 arc-manager 或 orchestrator 执行）
- **运行方式**: 每检测周期触发一次（周期可变，见第 6 节）

## 2. 七维疲劳检测体系

### 2.1 检测维度总览

| # | 维度 | 检测内容 | 权重 | 检测方法 |
|---|------|---------|------|---------|
| 1 | 爽点重复率 | 同类爽点出现的频率与模式相似度 | 0.25 | 模板匹配 + 频率统计 |
| 2 | 台词重复率 | 标志性台词/句式出现间隔 | 0.10 | 台词指纹库 + 间隔分析 |
| 3 | 情绪曲线分析 | 连续章节基调是否单一 | 0.15 | 情感曲线对比 + 方差分析 |
| 4 | 装逼密度 | 单位字数内装逼/显圣次数 | 0.10 | 行为模式识别 |
| 5 | 打脸模板匹配 | "看不起→展示实力→震惊"结构重复度 | 0.20 | 序列模式匹配 |
| 6 | 战斗模式分析 | 战斗描写结构相似度 | 0.10 | 场景结构向量对比 |
| 7 | 地图/场景复用 | 同一类型场景频繁出现 | 0.10 | 场景分类 + 频率统计 |

> **权重说明**: 权重和为 1.0。爽点重复率和打脸模板匹配权重最高（各 0.20-0.25），因为这两者是番茄 AI 文疲劳的主因。台词、装逼密度、战斗模式、地图复用为辅助信号。

### 2.2 维度一：爽点重复率（权重 0.25）

**检测目标**: 识别同一类爽点模式的过度使用。

**爽点分类体系**:

| 爽点类型 | 定义 | 示例 |
|---------|------|------|
| 身份碾压 | 显圣身份 → 对方震惊 | "我是龙国龙王" |
| 实力打脸 | 看不起 → 展示实力 → 震惊 | 废柴秒杀天才 |
| 财富碾压 | 炫富 → 对方跪舔 | 刷卡/买楼/包场 |
| 权威反转 | 被专家否定 → 专家被打脸 | 医术/鉴宝/赌石 |
| 关系反转 | 被看不起 → 背后势力现身 | "他是我大哥" |
| 智商碾压 | 对方算计 → 主角反杀 | 商战/官场/推理 |
| 系统奖励 | 达成条件 → 获得奖励 | 签到/升级/抽奖 |

**检测算法**:

```
1. 遍历检测周期内所有章节，提取每个章节的"爽点事件"列表
2. 对每个爽点事件，分类到爽点类型
3. 计算每种爽点类型的出现频率（次/章）
4. 对频率 > 阈值的类型，计算内部模式相似度：
   a. 提取该类型所有事件的模式向量（触发条件 → 展示方式 → 反应结果）
   b. 两两计算余弦相似度
   c. 取平均相似度作为该类型的重复得分
5. 最终得分 = max(各类型得分)
```

**评分规则**:

| 得分区间 | 含义 |
|---------|------|
| 0-0.3 | 正常多样性 |
| 0.3-0.5 | 某类爽点偏多，建议加新类型 |
| 0.5-0.7 | 明显重复，需要减少该类型 |
| 0.7-1.0 | 严重疲劳，必须插入新爽点类型 |

**相似度计算**:

```
同一爽点类型的两个事件，模式相似度计算：
- 触发条件相似（都是"被服务员看不起"→"展示身份"→"经理道歉"）→ +0.4
- 展示方式相似（都是"亮出龙国令牌"）→ +0.3
- 反应方式相似（都是"对方跪地求饶"）→ +0.3
→ 总相似度 = 0.4 + 0.3 + 0.3 = 1.0 完全重复

如果是"被保安看不起"→"打电话叫人"→"老板亲自迎接"
→ 触发条件相似 +0.3，展示方式不同 +0.0，反应部分相似 +0.1
→ 总相似度 = 0.4
```

### 2.3 维度二：台词重复率（权重 0.10）

**检测目标**: 标志性台词/句式过度使用导致的审美疲劳。

**台词指纹库**:

维护一个动态更新的台词指纹库，包含以下特征：

```
台词指纹 = {
  "text_hash": "md5(标准化后的台词文本)",
  "text": "就这？",
  "variants": ["就这?", "就这水平?", "就这点本事?"],
  "chapter_first_used": 15,
  "usage_count": 4,
  "last_usage_chapter": 47,
  "usage_intervals": [12, 9, 11],  // 使用间隔（章）
}
```

**检测算法**:

```
1. 扫描检测周期内所有角色的标志性台词
2. 台词指纹匹配（含变体模糊匹配）
3. 对每条台词计算：
   a. 使用间隔方差（稳定短间隔 → 疲劳信号强）
   b. 累计使用次数（次数越多 → 疲劳信号强）
4. 台词疲劳得分 = f(使用次数, 间隔方差, 周期内出现频率)
```

**常见疲劳台词列表**（示例）：

| 台词 | 典型疲劳周期 | 检测后建议替换 |
|------|-------------|--------------|
| "就这？" | 每 10 章 >1 次 | "不过如此" / "差得远" |
| "你算什么东西" | 每 15 章 >1 次 | "你有资格和我说话？" |
| "跪下" | 每 20 章 >1 次 | "认错" / "道歉" |
| "你惹错人了" | 每 20 章 >1 次 | 用行动代替台词 |
| "我记住你了" | 每 25 章 >1 次 | 减少使用或改为内心独白 |

### 2.4 维度三：情绪曲线分析（权重 0.15）

**检测目标**: 连续 N 章情绪基调单一导致的麻木。

**情绪标签体系**:

每章分配一个主要情绪标签：

| 情绪 | 标签 | 示例场景 |
|------|------|---------|
| 高潮 | climax | 战斗胜利、身份揭晓、打脸成功 |
| 紧张 | tension | 危机逼近、对决前奏、倒计时 |
| 压抑 | despair | 失败、损失、被压制 |
| 舒缓 | relief | 战斗后休整、温情日常、收获成果 |
| 悬疑 | mystery | 发现线索、谜团出现、伏笔暗示 |
| 平淡 | flat | 过渡章节、日常描写、背景交代 |

**检测算法**:

```
1. 为检测周期内每章标记主要情绪标签
2. 计算情绪序列的方差：
   - 高方差 → 情绪丰富，健康
   - 低方差 → 情绪单一，疲劳信号
3. 检测"连续同基调"：
   - 连续 5 章同基调 → 标记疲劳（不论是什么情绪）
   - 连续 5 章都是高潮 → 读者达到兴奋阈值，不再兴奋
   - 连续 5 章都是压抑 → 读者感到压抑、想弃书
   - 连续 5 章都是平淡 → 读者感到无聊、跳过
4. 检测"情绪循环"：
   - 检测是否出现周期性情绪模式（高潮→压抑→高潮→压抑...）
   - 周期模式重复 >3 次 → 标记可预测性疲劳
```

**疲劳评分**:

| 条件 | 得分 |
|------|------|
| 情绪方差 > 0.3，无连续同基调 >3 章 | 0-0.2 安全 |
| 连续 4-5 章同基调 | 0.2-0.4 轻度疲劳 |
| 连续 6-8 章同基调 或 情绪循环重复 >3 次 | 0.4-0.7 中度疲劳 |
| 连续 >8 章同基调 | 0.7-1.0 严重疲劳 |

### 2.5 维度四：装逼密度（权重 0.10）

**检测目标**: 单位字数内装逼/显圣行为过度集中。

**装逼行为分类**:

| 类型 | 识别特征 | 示例 |
|------|---------|------|
| 身份展示 | 亮出称号/令牌/证件 | "我是龙国龙王" |
| 实力展示 | 一招秒杀/碾压对手 | "一招，只用一招" |
| 财富展示 | 巨额消费/炫富 | "刷卡，不限额度" |
| 人脉展示 | 大人物现身撑腰 | "打电话叫来市长" |
| 知识展示 | 专业知识碾压 | 背诵医书/鉴赏古董 |
| 背景展示 | 背景势力暴露 | "我背后是龙组" |

**检测算法**:

```
1. 按检测周期统计总字数
2. 提取所有装逼/显圣事件
3. 计算装逼密度 = 装逼事件数 / 总字数 × 10000（每万字密度）
4. 对比基线密度（根据小说类型动态计算）：
   - 战神流基线：2-3 次/万字
   - 神豪流基线：1.5-2.5 次/万字
   - 修仙流基线：1-2 次/万字
   - 都市文基线：0.5-1.5 次/万字
5. 密度偏离基线程度 → 转化为 0-1 得分
```

**评分规则**:

| 密度 vs 基线 | 得分 |
|-------------|------|
| 低于基线 | 0-0.1（安全，密度不足可能不够爽） |
| 基线内 | 0-0.2（安全） |
| 超过基线 50% | 0.2-0.4（轻度警告） |
| 超过基线 100% | 0.4-0.7（中度疲劳） |
| 超过基线 200%+ | 0.7-1.0（严重，读者已麻木） |

### 2.6 维度五：打脸模板匹配（权重 0.20）

**检测目标**: "看不起→展示实力→震惊"三段式结构的重复程度。

**打脸模板结构**:

```
[看不起阶段]
  ├─ 轻视行为（嘲讽/贬低/无视）
  ├─ 主角低调（不争辩/不展示/伪装平凡）
  └─ 旁观者推动（煽风点火/落井下石）

[展示阶段]
  ├─ 触发事件（被逼到不得不展示 / 主动时机成熟）
  ├─ 实力展示（一招/一语/一物震惊全场）
  └─ 身份揭示（令牌/称号/背景曝光）

[震惊阶段]
  ├─ 对方震惊（表情/语言/动作的强烈反应）
  ├─ 地位反转（求饶/跪舔/态度 180° 转变）
  └─ 旁观者评价（"原来他才是大佬"）
```

**检测算法**:

```
1. 将检测周期内每章的场景序列化为"结构标签"
2. 使用滑动窗口匹配打脸模板的三个阶段
3. 对匹配到的每个打脸模式，提取结构向量：
   [看不起类型, 展示方式, 震惊强度, 持续时间, 结果类型]
4. 两两计算模式相似度（加权欧几里得距离）
5. 打脸模板疲劳得分 = 匹配到的打脸次数 / 检测周期长度 × 平均相似度
```

**相似度判定**:

| 比较维度 | 完全重复 | 部分重复 | 不重复 |
|---------|---------|---------|-------|
| 看不起类型 | 同样被服务员看不起 | 被不同身份的人看不起 | 没有被看不起环节 |
| 展示方式 | 同样亮令牌 | 亮令牌 vs 打电话叫人 | 完全不同 |
| 震惊强度 | 同样跪地求饶 | 求饶 vs 震惊不语 | 完全不同 |
| 结果类型 | 同样经理道歉 | 道歉 vs 赔偿 | 完全不同 |

**判定规则**:

- 相似度 > 70% → 标记为同一个打脸模板的变体
- 同一模板出现 >2 次/周期 → 疲劳信号
- 同一模板出现 >4 次/周期 → 严重疲劳

### 2.7 维度六：战斗模式分析（权重 0.10）

**检测目标**: 战斗描写结构/节奏的重复使用。

**战斗模式分类**:

| 模式 | 特征 | 典型流程 |
|------|------|---------|
| 秒杀流 | 一招解决，强调实力差距 | 嘲讽 → 出手 → 秒杀 → 震惊 |
| 胶着流 | 你来我往，强调技巧 | 试探 → 对攻 → 危机 → 反杀 |
| 蓄力流 | 前期被压制，后期爆发 | 被压制 → 蓄力 → 爆发 → 逆转 |
| 智斗流 | 以智取胜，非纯粹力量 | 设局 → 诱导 → 破局 → 取胜 |
| 群战流 | 一对多，展示范围能力 | 包围 → 展示 → 全灭 → 震撼 |
| 追逐流 | 追逃战，强调速度/地形 | 追逐 → 障碍 → 反制 → 脱逃 |

**检测算法**:

```
1. 提取检测周期内所有战斗场景
2. 对每个场景分配战斗模式标签
3. 统计各模式的频率分布
4. 对同类模式场景，提取结构向量：
   [开战方式, 攻防转换次数, 胜负方式, 战斗时长, 后续影响]
5. 计算同类模式内部的结构相似度
6. 战斗疲劳得分 = 同类模式占比 × 内部相似度
```

**评分规则**:

| 条件 | 得分 |
|------|------|
| 多种模式混合，无模式占比 >40% | 0-0.2 安全 |
| 某模式占比 40-60%，内部相似度 <0.5 | 0.2-0.4 轻度 |
| 某模式占比 >60%，或内部相似度 >0.7 | 0.4-0.7 中度 |
| 单一模式占比 >80%，内部相似度 >0.9 | 0.7-1.0 严重 |

### 2.8 维度七：地图/场景复用（权重 0.10）

**检测目标**: 同一类型场景/地图频繁出现。

**场景分类体系**:

| 场景类型 | 示例 | 典型使用周期 |
|---------|------|-------------|
| 都市街道 | 街头冲突、偶遇 | 每 10-15 章 |
| 高级餐厅 | 炫富、商务谈判 | 每 15-20 章 |
| 拍卖会/赌石场 | 捡漏、打脸 | 每 20-30 章 |
| 医院 | 治病救人、医学打脸 | 每 25-35 章 |
| 学校/学院 | 校园冲突、考试打脸 | 每 10-20 章 |
| 公司/办公室 | 商战、职场打脸 | 每 15-25 章 |
| 比武台/擂台 | 比武、挑战 | 每 20-30 章 |
| 宴会/酒会 | 社交、身份揭示 | 每 15-25 章 |
| 秘境/副本 | 冒险、寻宝 | 每 30-50 章 |
| 家庭/住宅 | 亲情、家族冲突 | 每 20-30 章 |

**检测算法**:

```
1. 为检测周期内每章标注主要场景类型
2. 统计各场景类型的出现频率
3. 计算场景多样性指数（Shannon 熵）：
   H = -Σ(pᵢ × log₂(pᵢ))
   其中 pᵢ = 第 i 类场景的出现比例
4. 对比健康多样性范围
5. 检测同一场景类型的连续使用（如连续 3 章在同一地图）
6. 场景疲劳得分 = f(多样性不足, 高频场景重复率)
```

**评分规则**:

| 多样性指标 | 得分 |
|-----------|------|
| 多样性指数 > 3.0（丰富） | 0-0.2 安全 |
| 多样性指数 2.0-3.0 | 0.2-0.4 轻度 |
| 多样性指数 1.0-2.0 | 0.4-0.7 中度 |
| 多样性指数 < 1.0 | 0.7-1.0 严重 |

## 3. anti-fatigue Collection Schema

### 3.1 MongoDB Collection: `anti_fatigue`

每条文档代表一个检测周期的结果。

```json
{
  "_id": "ObjectId",
  "project_id": "ObjectId（引用 projects 集合）",
  "period_id": "string（检测周期标识，如 'period_001'）",

  // ── 周期范围 ──
  "chapter_start": 1,
  "chapter_end": 20,
  "total_chapters_in_period": 20,
  "total_words_in_period": 120000,

  // ── 七维疲劳得分（0-1） ──
  "scores": {
    "excitement_repetition": {
      "score": 0.45,
      "detail": "身份碾压类爽点出现 6 次/20 章，内部模式相似度 0.72",
      "top_repeated_type": "身份碾压",
      "type_frequency": {
        "身份碾压": 6,
        "实力打脸": 4,
        "财富碾压": 3,
        "权威反转": 2,
        "关系反转": 1,
        "智商碾压": 0,
        "系统奖励": 0
      },
```

## 4. 疲劳阈值触发机制

### 4.1 三级阈值体系

依据**加权综合得分**判定当前疲劳状态。

**权重配置**:

| 维度 | 权重 | 说明 |
|------|------|------|
| 爽点重复率 | 0.25 | 核心指标，权重最高 |
| 打脸模板匹配 | 0.20 | 核心指标 |
| 情绪曲线分析 | 0.15 | 重要辅助指标 |
| 装逼密度 | 0.10 | 辅助指标 |
| 台词重复率 | 0.10 | 辅助指标 |
| 战斗模式分析 | 0.10 | 辅助指标 |
| 地图/场景复用 | 0.10 | 辅助指标 |

**加权总分计算公式**:

```
overall_score = Σ(维度得分 × 维度权重)
```

### 4.2 三级响应

```
总分 < 0.2：安全
  → 状态: "safe"
  → 动作: 仅记录，不触发任何干预
  → 日志: [ANTI-FATIGUE] Period X: SAFE (score=0.15)

0.2 ≤ 总分 ≤ 0.5：警告
  → 状态: "warning"
  → 动作: 记录 + 生成干预建议（不自动执行）
  → 发送 WARNING 事件到事件总线
  → arc-manager 可参考但不强制采纳
  → 日志: [ANTI-FATIGUE] Period X: WARNING (score=0.35)
          建议: 考虑减少同类爽点，引入新地图

总分 > 0.5：严重
  → 状态: "critical"
  → 动作: 记录 + 生成强制干预建议
  → 发送 CRITICAL 事件到事件总线（高优先级）
  → arc-manager 必须在下一周期内执行至少一项干预
  → 如果连续两个周期 critical，升级为"紧急模式"
  → 日志: [ANTI-FATIGUE] Period X: CRITICAL (score=0.62)
          强制干预: 必须插入新地图 + 引入新势力 + 转变节奏
```

### 4.3 紧急模式

当连续两个检测周期均为 `critical` 状态时，触发紧急模式：

```
紧急模式协议:
1. 暂停当前 Beat ARC 的正常推进
2. anti-fatigue agent 与 arc-manager 联合执行紧急干预
3. 必须在 3 章内完成至少 2 项干预策略（见第 5 节）
4. 干预执行后，缩短检测周期（从 20 章缩短到 10 章）
5. 如果下一个短周期仍然 critical → 建议作者手动介入
```

### 4.4 各维度独立告警

除综合阈值外，各维度也设有独立告警线：

| 维度 | 警告线 | 严重线 | 说明 |
|------|-------|-------|------|
| 爽点重复率 | >0.4 | >0.6 | 某一类爽点过度使用 |
| 台词重复率 | >0.35 | >0.55 | 标志性台词疲劳 |
| 情绪曲线分析 | >0.4 | >0.6 | 连续 5+/8+ 章同基调 |
| 装逼密度 | >0.4 | >0.65 | 密度超过基线 100%/200% |
| 打脸模板匹配 | >0.4 | >0.6 | 同样板 >2 次/4 次 |
| 战斗模式分析 | >0.4 | >0.6 | 单一模式 >60%/>80% |
| 地图/场景复用 | >0.4 | >0.6 | 多样性指数 <2.0/<1.5 |

> 当任一维度达到严重线时，即使综合得分 <0.5，也建议执行针对该维度的定向干预。

## 5. 干预策略

### 5.1 干预策略总览

| # | 策略类型 | 疲劳信号 | 干预力度 | 作者可控性 |
|---|---------|---------|---------|-----------|
| 1 | 插入新地图 | 场景多样性低、地图复用 | 中 | 高（可指定地图类型） |
| 2 | 插入副本/事件 | 爽点类型单一、模式重复 | 中 | 高（可指定事件类型） |
| 3 | 引入新势力 | 打脸对象单一、冲突模式固定 | 高 | 中（自动生成势力设定） |
| 4 | 转变节奏 | 情绪单一、装逼密集 | 中 | 中（可指定节奏方向） |
| 5 | 危机插入 | 整体疲劳分高、紧急模式 | 高 | 低（自动生成危机事件） |

### 5.2 策略一：插入新地图

**触发条件**:
- 场景复用得分 > 0.4（多样性指数 < 2.0）
- 或 紧急模式下优先执行

**策略说明**:

根据当前小说类型和已有地图，推荐下一个要跳转的地图类型：

| 当前地图 | 推荐跳转 | 叙事功能 |
|---------|---------|---------|
| 都市 | → 学院/校园 | 换环境，引入新社交圈 |
| 都市 | → 异界秘境/副本 | 换世界，引入新力量体系 |
| 学院 | → 都市/商业圈 | 从象牙塔到现实社会 |
| 学院 | → 异界战场 | 实战检验所学 |
| 异界/修仙 | → 都市/现代 | 反差感，现代身份暴露 |
| 修仙门派 | → 秘境/遗迹 | 探险、寻宝、新机缘 |
| 商业/公司 | → 慈善晚宴/艺术圈 | 换社交场景，不同冲突模式 |
| 家族/宅斗 | → 军政/官场 | 升级冲突层级 |

**执行方式**:

```json
{
  "strategy": "new_location",
  "target_location_type": "学院/校园",
  "reason": "当前都市场景复用率过高（高级餐厅×5，街道×4）",
  "suggested_chapter_range": "ch21-ch30",
  "narrative_hook": "主角收到一封来自龙魂学院的入学邀请函",
  "arc_impact": "开启学院 Arc，新地图新人物新冲突"
}
```

### 5.3 策略二：插入副本/事件

**触发条件**:
- 爽点重复率 > 0.4
- 或 打脸模板匹配 > 0.4
- 或 装逼密度 > 0.4

**策略说明**:

插入与当前主线不同类型的事件，打破模式循环。

| 当前主线类型 | 推荐插入事件 | 效果 |
|------------|------------|------|
| 打脸升级流 | 商业战争 | 换节奏，从武力到智斗 |
| 神豪消费流 | 慈善晚宴 | 换场景，从炫富到社会影响力 |
| 战神回归流 | 家族内斗 | 换冲突，从外部敌人到内部矛盾 |
| 修仙升级流 | 秘境探险 | 换模式，从修炼到冒险 |
| 都市异能流 | 国际事件 | 升级格局，从小范围到全球 |
| 官场晋升流 | 危机公关 | 换角度，从明争到暗斗 |

**执行方式**:

```json
{
  "strategy": "new_event",
  "target_event_type": "商业战争",
  "reason": "当前爽点模式以身份碾压为主（6/20 章），需要不同类型的冲突",
  "suggested_highlights": [
    "收购与反收购战",
    "股价狙击战",
    "董事会权力博弈"
  ],
  "narrative_hook": "主角名下公司突然遭遇恶意收购",
  "duration_chapters": "5-8"
}
```

### 5.4 策略三：引入新势力

**触发条件**:
- 打脸模板匹配得分 > 0.4（同样板重复）
- 或 综合疲劳分 > 0.5 且其他策略效果不足

**策略说明**:

引入新的敌对/联盟/中立势力，改变当前的冲突格局。

**新势力类型**:

| 势力类型 | 叙事功能 | 示例 |
|---------|---------|------|
| 新敌对势力 | 增加打脸对象的多样性 | 隐世家族、跨国集团、上古宗门 |
| 新联盟势力 | 提供新支持、新任务 | 神秘组织、龙组/超能局、商会联盟 |
| 中立第三方 | 制造意外变数 | 赏金猎人、国际仲裁组织、新闻媒体 |
| 隐藏势力 | 揭示世界观深度 | 黑暗世界、地下组织、远古守护者 |

**引入规则**:

```
1. 新势力的引入必须有合理的前因（不能凭空出现）
2. 新势力必须关联已有世界观设定（world_bible 中埋过伏笔）
3. 新势力的核心设定不能与已有势力雷同
4. 引入后至少存活 1 个 Phase ARC（不得用完即弃）
```

**执行方式**:

```json
{
  "strategy": "new_faction",
  "faction_type": "新敌对势力",
  "faction_name": "隐世家族·墨家",
  "reason": "当前打脸对象全是本地小势力，需要升级冲突层级",
  "backstory": "传承百年的豪门世家，掌控南方经济命脉",
  "introduction_chapter": 22,
  "arc_role": "下一个 Beat ARC 的主要冲突对象"
}
```

### 5.5 策略四：转变节奏

**触发条件**:
- 情绪曲线分析得分 > 0.4（连续同基调）
- 或 装逼密度得分 > 0.4

**策略说明**:

从当前叙事节奏向反方向调整，打破读者的阅读惯性。

**节奏转变方向**:

| 当前节奏 | 推荐转变 | 具体方法 |
|---------|---------|---------|
| 快节奏（连续高潮·打脸·爽） | → 慢节奏 | 插入 2-3 章温情/日常/修整 |
| 慢节奏（过渡·铺垫·日常） | → 快节奏 | 引入突发事件/危机 |
| 压抑节奏（连续失败·低谷） | → 上升节奏 | 安排逆袭/复仇/翻身 |
| 悬疑节奏（连续伏笔·谜团） | → 明朗节奏 | 揭示部分真相/线索明朗化 |
| 战斗节奏（连续战斗） | → 文戏节奏 | 政治博弈/感情线/谈判 |

**执行方式**:

```json
{
  "strategy": "change_pacing",
  "from_pacing": "fast（连续高潮7章）",
  "to_pacing": "slow（舒缓过渡）",
  "reason": "连续7章高潮导致读者情绪疲劳，需要3-5章缓降",
  "suggested_content": [
    "主角在庄园休整，与红颜知己互动",
    "回忆过去的温馨片段",
    "为下一段剧情做铺垫的日常篇"
  ],
  "duration_chapters": "3-5"
}
```

**悬疑元素注入**（可选）：

若需要在不减缓节奏的前提下制造新鲜感，可加入悬疑元素：

```
悬疑注入方法：
1. 在章节末尾留下未解之谜（不是 cliffhanger，而是信息缺口）
2. 引入神秘角色（身份不明，动机不明）
3. 发现前人遗留的线索/物品（暗示更大的世界观）
4. 主角能力出现异常波动（暗示力量体系更深层规则）
```

### 5.6 策略五：危机插入

**触发条件**:
- 综合疲劳分 > 0.5，且处于紧急模式
- 或 连续两个周期 critical

**策略说明**:

最高级别的干预——制造突发危机，强制改变叙事轨道。

**危机类型**:

| 危机类型 | 描述 | 疲劳维度覆盖 |
|---------|------|-------------|
| 突发灾难 | 地震、火灾、病毒爆发 | 情绪、场景、节奏 |
| 身份曝光 | 主角隐藏身份被公开 | 爽点、打脸、势力 |
| 倒计时事件 | 限时任务、倒计时危机 | 情绪、节奏、装逼 |
| 盟友背叛 | 信任角色突然背叛 | 势力、情绪、打脸 |
| 重大损失 | 主角失去关键能力/财产/人脉 | 情绪、节奏、势力 |

**执行方式**:

```json
{
  "strategy": "crisis_insertion",
  "crisis_type": "身份曝光",
  "severity": "high",
  "reason": "紧急模式：连续2周期 critical（score=0.62, 0.58）",
  "crisis_detail": "主角龙国龙王身份被狗仔队偷拍曝光，全网热议",
  "expected_effects": [
    "改变当前打脸模式（不再需要主动展示身份）",
    "引入新势力（国家机构、敌对势力关注）",
    "情绪转折（从爽到危机感）",
    "场景变更（从日常到媒体发布会/逃亡）"
  ],
  "execution_urgency": "immediate（下一章必须引入）"
}
```

### 5.7 干预策略组合推荐

根据不同疲劳画像，推荐策略组合：

| 疲劳画像 | 推荐组合 | 优先级 |
|---------|---------|-------|
| 场景疲劳型（场景分高 + 爽点分中） | 插入新地图 + 插入副本/事件 | 先换地图，再换事件类型 |
| 模式疲劳型（打脸分高 + 爽点分高） | 引入新势力 + 转变节奏 | 先改冲突对象，再调整节奏 |
| 情绪疲劳型（情绪分高 + 节奏单ー） | 转变节奏 + 危机插入 | 先调节奏，必要时制造危机 |
| 全面疲劳型（所有维度 >0.4） | 危机插入 + 新地图 + 新势力 | 全面重置，最高优先级 |
| 台词疲劳型（台词分高，其余正常） | 替换台词（本地修复，不触发策略） | 仅替换，无需大规模干预 |

## 6. anti-fatigue Agent 执行优先级与调用时机

### 6.1 系统定位

anti-fatigue agent 是一个**周期性质量监控 Agent**，位于 pipeline 的**分析层**（与 analytics agent 同级），在写作层（draft/editor）之后执行。

### 6.2 调用时机

| 触发方式 | 条件 | 周期 | 优先级 | 说明 |
|---------|------|------|-------|------|
| 周期检测 | 每完成 20 章 | 20 章 | 常规 | 标准检测周期，写入 anti_fatigue collection |
| 紧急检测 | 综合得分 > 0.5 | 缩短至 10 章 | 高 | 加速监控，直到得分 < 0.3 |
| 触发检测 | arc-manager 请求 | 按需 | 中 | 当 arc-manager 需要疲劳数据做决策时 |
| 手动检测 | 作者主动触发 | 按需 | 中 | 提供 force_check 接口 |

### 6.3 执行流程

```
[触发检测]
    │
    ▼
1. 加载数据
   ├── 从 chapter_memory 加载最近 N 章（N=检测周期长度）
   ├── 从 anti_fatigue 加载上一个周期的检测结果
   └── 从 arc_plans 加载当前 active Beat ARC 规划
    │
    ▼
2. 七维检测
   ├── 2.1 爽点重复率检测
   ├── 2.2 台词重复率检测
   ├── 2.3 情绪曲线分析
   ├── 2.4 装逼密度计算
   ├── 2.5 打脸模板匹配
   ├── 2.6 战斗模式分析
   └── 2.7 地图/场景复用检测
    │
    ▼
3. 综合评分
   ├── 计算加权总分
   ├── 对比上周期得分趋势
   └── 判定状态（safe/warning/critical）
    │
    ▼
4. 生成干预建议
   ├── 根据疲劳画像匹配推荐策略
   ├── 按优先级排序
   └── 生成可执行的干预方案
    │
    ▼
5. 写入 MongoDB
   ├── 将完整检测结果写入 anti_fatigue collection
   └── 更新 project 的 latest_fatigue_score 字段
    │
    ▼
6. 发送事件
   ├── 如果 status=warning → 发送 FATIGUE_WARNING 事件
   ├── 如果 status=critical → 发送 FATIGUE_CRITICAL 事件
   └── 如果 status=safe → 发送 FATIGUE_SAFE 事件（仅日志）
    │
    ▼
7. [可选] 紧急模式
   ├── 检查是否连续两个 critical
   └── 如果触发 → 执行紧急模式协议
```

### 6.4 资源消耗估算

| 操作 | 预估耗时 | 说明 |
|------|---------|------|
| 数据加载（20 章 chapter_memory） | ~2 秒 | MongoDB 查询 |
| 七维检测计算 | ~3-8 秒 | 主要耗时在打脸模板匹配和情绪分析 |
| 综合评分 + 干预建议生成 | ~2 秒 | LLM 调用用于生成建议 |
| MongoDB 写入 | ~1 秒 | 单文档写入 |
| 总计 | ~8-13 秒 | 20 章周期，可接受 |

### 6.5 与 pipeline 的关系

```
写作 pipeline（每次 3 章 batch）:
  draft → editor 1st pass → editor 2nd pass → anti-repetition
  → compliance → memory-manager → [下一 batch]
  
分析 pipeline（每 20 章）:
  anti-fatigue agent（当前系统）
  analytics agent（读者情绪/留存分析）
  arc-manager recalc（基于上述两个 agent 的输出调整 Beat ARC）

关系说明：
- anti-repetition 是"微观门禁"——每章检查，拒绝重复
- anti-fatigue 是"宏观监控"——每 20 章检查，预防疲劳
- 两者互补：anti-repetition 管局部，anti-fatigue 管整体
```

## 7. 与 arc-manager 的集成

### 7.1 集成原理

anti-fatigue agent 的检测结果直接影响 arc-manager 的 ARC 调整决策。两者通过**事件总线**和**共享状态**双向通信。

### 7.2 anti-fatigue → arc-manager 的事件

| 事件名称 | 负载 | 触发 arc-manager 动作 |
|----------|------|---------------------|
| `FATIGUE_SAFE` | `{period_id, overall_score < 0.2}` | 无（仅日志） |
| `FATIGUE_WARNING` | `{period_id, overall_score, scores, suggestions}` | recalc 时参考疲劳数据调整 Beat ARC |
| `FATIGUE_CRITICAL` | `{period_id, overall_score, scores, interventions}` | 必须在下一周期执行至少一项干预 |
| `FATIGUE_EMERGENCY` | `{period_id, consecutive_critical_count, scores, interventions}` | 暂停当前 Beat ARC，执行紧急模式 |

### 7.3 疲劳数据对 ARC 调整的影响

**recalc（重算 Beat ARC 方向）时**:

arc-manager 在每 10 章的 recalc 中，读取最新的 anti_fatigue 评分作为输入参数：

```json
// arc-manager recalc 时的参考数据
{
  "fatigue_scores": {
    "overall": 0.47,
    "significant_dimensions": ["face_slapping_template:0.65", "emotion_curve:0.60"]
  },
  "suggested_actions": {
    "adjust_frequency": "减少身份碾压类爽点，增加智斗类冲突",
    "adjust_pacing": "插入 2-3 章舒缓章节",
    "adjust_locations": "从都市跳转至学院地图"
  }
}
```

**对应的 ARC 调整决策**:

| 疲劳信号 | ARC 调整方向 | 具体操作 |
|---------|-------------|---------|
| 爽点重复率 > 0.5 | 调整 Beat ARC 的 conflict_type | 从"实力冲突"切换到"智斗冲突"或"情感冲突" |
| 打脸模板匹配 > 0.5 | 更换 Beat ARC 的 antagonist | 引入新反派/更换对抗方式 |
| 情绪曲线分 > 0.5 | 调整 Beat ARC 的 emotional_arc | 重新设计剩余章节的情绪起伏序列 |
| 场景复用 > 0.5 | 在 Beat ARC 中规划新地图 Arc | 新增一个包含新地图的 Beat |
| 综合得分 > 0.5 | 触发 Phase ARC 的 reconstruct | 重新规划当前 Phase 后续 Beat 的结构 |
| 连续 critical | 触发重建计划 | 考虑提前结束当前 Phase，进入下一 Phase |

### 7.4 ARC 结构调整映射

```
疲劳类型       →     ARC 调整
────────────────────────────────────────────
爽点类型单一    →     更换 Beat ARC 的 primary_conflict_type
打脸对象固定    →     更换 Beat ARC 的 antagonist_id + antagonist_archetype
战斗模式重复    →     在 twist_schedule 中增加非战斗冲突
场景单一        →     新增 Beat ARC（新地图主题）
情绪单调        →     修改 emotional_arc 的情感起伏设计
全面疲劳        →     加速 Phase 进程，提前进入高潮阶段
```

### 7.5 共享状态：arc_fatigue_bridge

anti-fatigue agent 和 arc-manager 共同维护一个桥接状态：

```json
{
  "_id": "ObjectId",
  "project_id": "ObjectId",
  "period_id": "string",
  "fatigue_snapshot": {
    "overall_score": 0.47,
    "status": "warning",
    "scored_at": "ISODate"
  },
  "arc_status": {
    "active_phase_id": "phase_002",
    "active_beat_id": "beat_007",
    "beat_progress": 0.65
  },
  "intervention_status": {
    "pending_interventions": 2,
    "applied_interventions": 1,
    "last_intervention_applied_at": "ISODate",
    "effectiveness_monitoring": true
  },
  "last_sync_at": "ISODate"
}
```

### 7.6 补偿机制联动

当 fatigue 触发 critical 时，arc-manager 的补偿机制（见 dynamic-arc-manager.md 第 5 节）联动激活：

| 触发条件 | 补偿动作 | 联动说明 |
|---------|---------|---------|
| FATIGUE_WARNING + 读者情绪低迷 | 插入高情感冲击章节 | anti-fatigue 提供疲劳方向，analytics 提供情绪数据 |
| FATIGUE_CRITICAL + 节奏过慢 | 压缩后续内容 + 换地图 | anti-fatigue 建议换地图，arc-manager 执行压缩 |
| FATIGUE_EMERGENCY + 读者流失 | 执行救火协议 | anti-fatigue 提供干预方案，arc-manager 统筹执行 |

## 8. 实现注意事项

### 8.1 数据依赖

anti-fatigue agent 的运行依赖于以下数据的可用性：

| 数据 | 来源 Collection | 必须/可选 | 说明 |
|------|---------------|-----------|------|
| 章节正文或摘要 | chapter_memory | 必须 | 用于文本分析和模式提取 |
| 章节情绪标签 | chapter_memory.emotion_tone | 必须 | 情绪曲线分析的基础 |
| 场景信息 | chapter_memory.scene_type | 推荐 | 若不存在，从正文提取 |
| 角色出场记录 | chapter_memory.characters | 可选 | 辅助分析 |
| 上一个周期检测结果 | anti_fatigue | 推荐 | 趋势对比 |

### 8.2 性能优化

```
1. 懒加载模式：仅加载检测周期范围内的数据
2. 缓存模式：同一周期内多次触发检测时，缓存中间计算结果
3. 渐进式检测：先跑轻量维度（台词/场景），分数超标再跑重量维度（打脸模板/情绪曲线）
4. 异步写入：MongoDB 写入操作异步执行，不阻塞主流程
5. 向量化：打脸模板和战斗模式的匹配使用预计算向量，不每周期重新提取
```

### 8.3 增量检测

对于常规周期性检测，支持增量模式——只分析新增的章节数据：

```
全量检测（首次或紧急模式）:
  分析整个检测周期的所有章节（20 章）

增量检测（常规周期）:
  1. 读取上一个周期的检测结果
  2. 只分析新增加章节（20-40 章中新增的 21-40 章）
  3. 与上一个周期的结果合并计算
  4. 优点：节省 50% 的计算量
  5. 缺点：无法检测跨周期的模式变化
```

### 8.4 人工兜底

```
1. 所有干预建议仅为建议——最终执行权在 arc-manager 或作者手中
2. 作者可手动设置 force_fatigue_score，覆盖自动检测结果
3. 作者可禁用某个维度的检测（如：特定题材不需要检测装逼密度）
4. 作者可手动触发紧急检测
5. 提供 force_intervention 接口，让作者主动要求执行某项干预策略
```

### 8.5 与 V2 anti-repetition 的关系

| 维度 | V2 anti-repetition | V3 anti-fatigue |
|------|-------------------|-----------------|
| 检测范围 | 单章 vs 历史 50 章 | 周期（默认 20 章）vs 历史周期 |
| 检测方法 | 模式匹配 + 阈值判定 | 多维度加权 + 趋势分析 |
| 输出粒度 | 单章通过/拒绝 | 全局疲劳度 + 维度拆分 |
| 干预形式 | 退回重写 + 替换建议 | 策略级干预（地图/势力/节奏） |
| 与 ARC 关系 | 独立运行 | 深度集成到 ARC 管理 |
| 运行频率 | 每章 | 每 20 章 |
| 存储 | anti_repetition collection | anti_fatigue collection |

> **共存策略**: V2 anti-repetition 继续作为每章的"微观门禁"运行，V3 anti-fatigue 作为"宏观监控"并行运行。两者不冲突，互补。

### 8.6 术语表

| 术语 | 定义 |
|------|------|
| 检测周期 | 一次完整七维检测覆盖的章节范围（默认 20 章） |
| 综合得分 | 七维加权总分（0-1），表示当前疲劳程度 |
| 疲劳画像 | 七维得分的分布特征，用于匹配干预策略 |
| 干预策略 | 五大类疲劳干预手段（地图/事件/势力/节奏/危机） |
| 紧急模式 | 连续两个 critical 周期触发的最高级别响应 |
| 趋势分析 | 对比相邻周期的得分变化，判定疲劳是改善还是恶化 |
| 爽点类型 | 七种爽点模式的分类体系 |
| 打脸模板 | "看不起→展示实力→震惊"的三段式结构 |
