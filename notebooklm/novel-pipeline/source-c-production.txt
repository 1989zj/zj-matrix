=== Hermes Agent 多Agent写小说：生产部署与故障处理 ===

=== 成本估算 ===

每章（约2000-2600字）：
  输入 token: ~40K（Context Packet + 最近5章 + 角色档案）
  输出 token: ~8K（正文 + 编辑审校）
  LLM 调用次数: draft(1) + editor(1) + validate(1) = 3 次/章
  每轮 3-5 章 ≈ 4.5 分钟 ≈ 144K in / 24K out tokens

10 万字 ARC（约 40 章）：
  总 token: 约 5.76M in / 0.96M out
  LLM 成本（以 DeepSeek 约 $0.5/M in / $2/M out 计）≈ $2.88 + $1.92 ≈ $4.80

=== 超时与恢复机制 ===

600s timeout 陷阱：
  novel-factory new 的 delegate_task 有 600s 子任务超时限制。
  3万字项目（含 Research + Outline + Character + Draft × N + Editor × N）在第 1 章 Editor 阶段即超时。
  解法：new 只做骨架（~2 章），continue 续写后续（每轮 3-5 章）。

Orchestrator 上下文压缩卡死：
  现象：context compaction 2+ 次后，orchestrator 反复读取-修复-重写同一批文件，不再推进新章节。
  诊断信号：超过 3 分钟无新输出、output_preview 重复同一段内容、草稿文件已在磁盘但无 snapshot/events 产生。
  恢复步骤：
    1. 确认草稿已写入磁盘：ls -la /root/novel-factory/<slug>/drafts/chapter_N.md
    2. 读开头确认内容完整
    3. kill 卡死的 orchestrator 进程
    4. 手动运行 validate-chapter.py check
    5. 手动写入 event_log（event_type 必须是枚举值：chapter_started / chapter_generated / chapter_validated / editor_completed / snapshot_saved 等）
    6. 手动写入 snapshot_store + chapter_snapshots（含完整正文）
    7. novel-factory continue '书名' 重续
  核心：草稿文件（磁盘）是 master，MongoDB 是辅助状态层。即使 orchestrator 挂掉，已写入磁盘的章节不丢失。

=== 安全规则 ===

  - 所有产出写入 MongoDB novel_factory（不依赖 GitHub 做持久化存储）
  - novel 数据库只做 V1 兼容层，不做创作主库
  - 对话引号必须用英文直引号 U+0022，禁止中文角括号（通过 normalize-quotes.py 自动化兜底）
  - pipeline 产出每次自动写入 event_log，不删不改历史记录
  - 短篇（≤2万字）也走完整 V3 pipeline，不简化持久化流程

=== 故障模式 ===

1. DeepSeek 503 导致 novel-factory 直接失败
  症状：API 瞬时过载，重试 3 次后退出
  处理：等 API 恢复后重新运行 new（从头开始）。
  如果有之前产出的 research/outline/character 文件，备份后用 continue 续写

2. UTF-8 编码损坏导致 Python 读不全章节文件
  症状：orchestrator 输出的 .md 文件含坏字节（如 0x90），
  导致 open().read() 只读入前半段（11324 字节实际只读到 4045 字符）
  修复：用 rb 模式读取原始字节，手动验证 UTF-8 序列合法性并跳过坏字节

3. MongoDB $jsonSchema 校验失败
  常见错误：updated_at 传了 datetime 对象而非 ISO 字符串、
  stats 缺少 required 字段、
  factions 传了 list 而非 dict（AttributeError: 'list' object has no attribute 'items'）
  修复：sync 脚本中需 isinstance 分支处理 + 正确序列化

4. V1→V2 迁移角色出场审计遗漏
  问题：chapter_memory.summary 只有正文前 200 字截取，没有标注出场角色
  影响：ARC planner 和 analytics 无法准确知道角色活跃度
  修复：逐章全文扫描角色名 + 别名，补充到 summary 字段

=== 生产建议 ===

- background=true 模式用于 >2 章的写作任务（bypass 600s 前台限制）
- 每 50 万字做一次全量刷新（analytics + arc-planner + lore 一致性审计）
- ARC 之间留 3-5 章过渡缓冲（场景休息、新危机萌芽）
- 预留 15-20% 字数给意外发展方向
- 3 轮反馈循环不通过 = 停，等人工干预，防止无限消耗 token
