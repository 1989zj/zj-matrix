=== Hermes Agent 自动客服：部署、安全与故障处理 ===

=== 部署环境 ===

当前 Hermes Agent 运行环境：
  CPU: Intel Xeon E5-2670 v2（无 GPU）
  RAM: 8GB
  OS: Linux
  框架: Hermes Agent（DeepSeek API 驱动）
  投递: 飞书（默认 home channel）

客服相关数据：
  知识库: ~/.hermes/cs-faq.yaml（FAQs）
  话术模板: ~/.hermes/cs-templates.yaml
  质检报告: ~/.hermes/cs-reports/
  所有 cronjob 脚本: ~/.hermes/scripts/

=== 安全规则 ===

1. 客户隐私
   - LLM 生成的回复中不包含客户姓名、手机号、地址等 PII
   - 监控脚本检测到 PII 时自动脱敏（用 *** 替换）
   - 质检报告只输出统计数据，不展示完整对话原文
   - 知识库中的客户案例必须去标识化

2. 输出安全
   - LLM 回复必须有置信度过滤（< 0.8 必须转人工）
   - 自动回复不得包含价格承诺/赔偿金额等敏感决策
   - 所有自动回复末尾追加「如需进一步帮助，请回复转人工」

3. 审计与回滚
   - 每条 LLM 生成的回复记录到本地日志
   - 日志保存 30 天
   - 支持追溯某条回复由哪个 cronjob / task 生成

=== 故障模式 ===

1. LLM 回复质量差
   症状：答非所问、语气错误、提供错误信息
   防范：
   - 置信度阈值过滤（< 0.8 转人工）
   - FAQ 知识库 + RAG 模式而非纯 LLM 发挥
   - prompt 中明确限制"不知道就说不知道"

2. 分类错误导致工单投递错人
   症状：投诉类工单发给售前组
   防范：
   - 分类结果附带 confidence 字段
   - confidence < 0.7 的工单投递到"待确认"队列
   - 每周人工复核分类准确率

3. 情绪监测过度敏感
   症状：客户只是打字风格急但非负面，频繁触发升级
   防范：
   - 阈值设为 0.2（非常负面才告警，而不是一般负面）
   - 结合消息长度过滤（太短的消息不做情绪分析）
   - 同一客户 30 分钟内只触发一次升级

4. FAQ 匹配失败
   症状：常见问题未匹配到知识库，全部转人工
   防范：
   - 每月分析转人工记录，提炼新 FAQ
   - 使用 embedding 相似度搜索（而非纯关键词）
   - 相似度 > 0.7 时算匹配，而非要求精确匹配

5. 超时监控误报
   症状：工单已被人工回复但系统未标记
   防范：
   - 检查工单状态而非仅检查时间戳
   - 增加 grace period（超过阈值后再等 5 分钟才告警）
   - 监控脚本每轮检查时清除已回复工单

=== 实施路线图 ===

第 1 周：FAQ 自动回复
  搭建知识库（30 条高频问题）
  配置手动触发回复生成
  置信度 > 0.85 自动回复，测试一周准确率

第 2 周：超时监控 + 情绪监测
  部署 cronjob（no_agent 零成本）
  设置飞书告警
  跑一周看误报率，调阈值

第 3 周：工单分类路由
  分类 prompt 设计
  delegate_task 配置三条分类线路
  手动验证 50 条工单，调优 accuracy

第 4 周：质检抽检 + 知识库一致性
  cronjob 每周一执行质检
  积累两周数据后调整评分标准
  进入迭代优化阶段

=== 一句话原则 ===

自动回复要"有兜底"——不确定就转人工，
不要自作聪明给出错误承诺。
